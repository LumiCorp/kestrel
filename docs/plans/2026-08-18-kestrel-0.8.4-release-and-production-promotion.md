# Kestrel 0.8.4 release and production promotion

## Goal

Ship one canonical 0.8.4 version across all workspace manifests, nine public
npm packages, CLI/TUI, signed Desktop, Kestrel One, Docs, and six production
images. Packages remain Stable. Desktop and Kestrel One remain Beta.

Use two ordinary pull requests:

1. `asher/release-0.8.4` to `main` for versioning, documentation, Desktop
   downgrade safety, and release tooling.
2. `main` to `production` after candidate artifacts pass.

Public release notes cover the complete v0.8.0 to v0.8.4 change. The production
deployment delta is PRs #383 through #391 plus this release preparation.

## Candidate qualification

Run from a clean Node 22 checkout of the release branch:

```bash
pnpm install --frozen-lockfile
pnpm version:check
pnpm validate
pnpm validate:process
pnpm validate:postgres
pnpm validate:chromium
pnpm ecosystem:release-check
pnpm docs:test
pnpm docs:build
pnpm docs:drift
pnpm desktop:package:dir
```

Run `desktop:package-smoke` under direct supervision. Validate Desktop schema
12 from public 0.7 and 0.8.0 settings, including Projects, providers, models,
appearance, approvals, MCP and OAuth registrations, capability packs, Keychain
credentials, and plugin lifecycle state. The pre-v12 backup must be byte-exact,
one-time, permission-restricted, and usable by the prior client. Retired
workflow-App identifiers must disappear.

Validate migration 0076 against production-shaped PostgreSQL data. Existing
schedules receive fallback titles, existing runs receive title snapshots,
scheduled and test triggers remain distinguishable, request IDs remain unique,
and previous application code tolerates the additive migration.

## Staging

After the release PR merges:

1. Create the ordinary `v0.8.4` tag.
2. Build package tarballs from the tagged state.
3. Publish Protocol, Conversation, Memory, Workspace Skills, SDK, Next, AI SDK,
   Observability, and Runtime/CLI under `release-0.8.4`, in that order.
4. Install the staged Runtime/CLI in clean macOS arm64 and Linux x64
   environments; verify version, TUI, Local Core, imports, and a basic turn.
5. Build the CLI archive and checksum.
6. Produce signed, hardened, notarized Desktop DMG and ZIP artifacts.
7. Pass Desktop release, Gatekeeper, LaunchServices, relaunch, persistence, and
   offline-turn gates.
8. Upload immutable 0.8.4 updater artifacts without moving stable.
9. Create a draft GitHub v0.8.4 release with notes, assets, and checksums.

Conversation is a first public npm publication. Confirm its package identity
and organization permission before publishing any package. Any candidate
failure returns to the release branch and repeats qualification and staging.

Candidate evidence proves immutable Desktop artifacts exist while stable is
unchanged. Operational evidence retains versions, dist-tags, checksums,
Developer ID signing, notarization, Gatekeeper, migration results, deployment
health, and canaries. It does not require package `gitHead`, provider revision,
or cross-channel commit equality.

## Production promotion

Run `pnpm production:cutover:preflight`, merge the protected `main` to
`production` pull request, and allow the independent Vercel deployments for
Kestrel One and Docs. Confirm migration 0076 applied once. Verify auth, an
existing Project and Thread, a new shared Thread, Mission Control, plugins,
action-bound approval, schedule creation, a manual schedule test, and public
documentation. Stop before image activation if either Vercel surface or the
migration check fails.

Publish all six images manually with the 0.8.4 tag:

```bash
pnpm production:image:publish --role <role> --tag 0.8.4
```

The roles are `workspace-runtime`, `environment-router`, `preview-edge`,
`turn-worker`, `control-worker`, and `runpod-worker`. Fly and RunPod remain
manual operations; no deployment workflow owns them.

Record each previous target tag. Qualify a disposable Workspace Runtime and
Environment Router canary, including repeated retirement, shutdown, recovery
beyond 120 seconds, and a real recovered Thread. Update exact Fly Machines one
at a time with `production:fly:machine`, update each Environment runtime tag
with `apps/web runtime:update`, and verify health after every target. Prove
Preview Edge ingress and routing, an interactive streamed Turn Worker result, a
scheduled approval-gated Control Worker action, and managed inference through
RunPod Worker. Activate 0.8.4 with `production:runtime:activate` and the
successful canary operation before advancing remaining intended Environments.

## Public cutover and closeout

After every production canary passes:

1. Publish GitHub v0.8.4 and mark it Latest.
2. Move `latest` to 0.8.4 for all nine npm packages and confirm clean installs.
3. Move Desktop stable from 0.7.0 to 0.8.4.
4. Run isolated signed 0.7.0 to 0.8.4 and installed 0.8.0 to 0.8.4 OTA tests.
5. Verify signatures, relaunch, version, user state, Mission Control, Local
   Core/PGlite, providers, Keychain credentials, plugin migration, settings
   backup, and updater cleanup for both paths.
6. Remove 0.7.0 from the current/stable presentation while retaining immutable
   versioned artifacts for rollback and history.
7. Delete stale GitHub environments `Production`, `Production – Docs`, and
   `Production – One`; add no replacements.
8. Recheck every public page and installation command.

Closeout requires GitHub Latest, npm latest, Desktop stable, Kestrel One, Docs,
and all six production image roles to report 0.8.4. Cutover evidence includes
passing 0.7.0 to 0.8.4 and 0.8.0 to 0.8.4 Desktop transitions.

## Rollback

- npm: move `latest` back; never unpublish 0.8.4.
- Desktop before migration: restore stable to 0.7.0.
- Desktop after migration: quit Kestrel, restore
  `desktop-settings.pre-v12.json`, then reinstall the previous signed app.
- Vercel: restore the previous production deployment.
- Database: leave additive migration 0076 applied.
- Fly and RunPod: restore each recorded previous image tag one target at a time.
- Runtime activation: restore the previous default tag before updating affected
  Environments.

Healthy independent channels remain advanced unless compatibility requires a
coordinated rollback.

The command-level manual rollout procedure is maintained in the
[production delivery runbook](../production-delivery-channels.md).
