# Kestrel 0.8 documentation inventory

## Question

Which documentation pages exist today, which ones need to change for the unified Kestrel 0.8 release, and which new pages are justified by product and runtime changes since `v0.7.0`?

## Answer

The docs need a structured 0.8 rewrite, not a version-only pass.

- The registry contains **80 public pages**, one internal archive gateway, and ten archived routes.
- **20 public pages** still contain current-line `0.7` language.
- **66 public pages** reference source that changed after `v0.7.0`.
- Only **27 of those 66 pages** changed alongside their referenced source, leaving **39 source-changed pages without a corresponding docs update**.
- The content tree contains **15 unregistered MDX files**. Several are valuable source material that should become public pages; others duplicate the current information architecture or belong in maintainer documentation.
- The registry still points at **ten archived files that were deliberately deleted** by `dd54ff1a` (`docs: purge stale planning records`). Those routes should be removed from the registry rather than restoring obsolete content.

The recommended 0.8 docs program is:

1. Rewrite release, installation, compatibility, product gateway, and migration pages as release blockers.
2. Expand product and operator pages whose owning source changed materially.
3. Add ten pages for reader jobs that have no clear owner today.
4. Publish three strong orphaned sources under supported routes.
5. Reconcile the remaining orphaned and stale archive entries before declaring the docs build release-ready.

The inventory is grounded in the current [`pageRegistry`](../../apps/docs/lib/content-registry.ts), page frontmatter and body content under [`apps/docs/content`](../../apps/docs/content), centralized release data in [`apps/docs/lib/release.ts`](../../apps/docs/lib/release.ts), and the repository delta from `v0.7.0` through `dff6e2b7`.

## Inventory method

`Delta` compares each page and its declared `sourceRefs` with `v0.7.0`:

- **D+S** — both the docs page and at least one owning source changed.
- **S** — owning source changed, but the page did not. This is the highest drift-risk class.
- **D** — page changed while its declared sources did not.
- **—** — neither changed according to the registry mapping; the page may still need a release or information-architecture update.

`Priority` means:

- **P0** — required before publishing 0.8 documentation.
- **P1** — substantive 0.8 expansion required in the integration push.
- **P2** — targeted verification or smaller refresh.
- **H** — historical content that must remain accurate as history, not be rewritten as current guidance.

Word counts are rough lexical counts used only to expose unusually thin pages. They are not quality scores.

- **Start:** add `/start/runtime-model` after Architecture.

- **Reference:** add Runtime Profiles and Providers, Recovery, Approvals and Effects, Tool Contracts, and Reasoning and Agent Progress.
- **CLI/TUI:** expose `/cli/install` before the command suite.

Do not create separate top-level Runtime, Packages, Apps, or Deploy sections. Their orphaned gateway pages duplicate the current six-journey model and would fragment navigation.

## Contradictions and unknowns

- The registry’s archived routes contradict the intentional deletion history. The safe resolution is removal, but `/archive` should be checked for any external links before route behavior changes.
- Several pages declare a single source file even though the 0.8 behavior spans contracts, services, migrations, and tests. Their `sourceRefs` must be expanded as part of the rewrite or future drift checks will remain misleading.
- `updatedAt` currently reflects editorial updates, not proof that every example was executed. The 0.8 pass should distinguish editorial freshness from verified examples, either through existing governance metadata or a narrowly added verification field.
- The active Desktop onboarding slice is not yet merged into current `main`. Desktop first-run and troubleshooting copy should be finalized only after that implementation lands; the page ownership and required subjects are already clear.
- Public package and artifact URLs should remain centralized and unresolved until the exact `v0.8.0` release assets exist. Preview copy can describe the contract without publishing dead download links.
