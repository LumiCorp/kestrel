Kestrel separates user experience from trusted execution. Desktop, Kestrel One, CLI/TUI, and SDK applications initiate work; Local Core or a remote runner executes it under explicit identity, profile, provider, tool, memory, budget, and policy contracts.

## Local and remote deployments

Desktop and local terminal workflows supervise Local Core beside the user’s project. Server applications may call Local Core or an authenticated remote runner. Kestrel One uses a Vercel application, PostgreSQL and supporting services, queue workers, and Fly-hosted Environment/image roles. The browser stays outside provider and runner credential boundaries.

## The durable runtime

The Runtime advances turns and persists conversation history, stream/subscription events, terminal results, Mission Control records, recovery decisions, approval evidence, memory provenance, budget allocations, evaluation results, and replay material through their owning stores.

## Authority and control

Actor and tenant/organization identity enter at the trusted application boundary. Profiles and provider registry entries control runtime/model behavior. Mission Control owns project work; operator control owns live conversations; external approval grants own consequential effects; execution-boundary policy owns tools, filesystems, Docker, MCP, and network access.

## Product and integration surfaces

Desktop, Kestrel One, and CLI/TUI render different experiences over the same concepts. Protocol and SDK packages expose typed contracts. Next.js, AI SDK, compatible HTTP, Memory, Observability, and Workspace Skills adapt only the boundary they own.

## Build and release identity

The semantic version identifies the product contract. Exact source revision identifies code. Desktop artifacts add signature and checksum. Hosted systems add migrations, Vercel deployment, worker revision, and immutable Fly image digests. A production claim requires the complete identity.
